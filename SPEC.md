# EasySend — техническое задание

Версия документа: 1.0 (черновик от 2026-08-07)

## 1. Суть

Кросс-платформенное приложение для простой пересылки файлов и папок между
устройствами в пределах одной локальной или маршрутизируемой сети. Без
интернета, без облака, без учётных записей и серверов-посредников.

Платформы v1: **Android, Linux, Windows**. Фреймворк: **Flutter (Dart)**.

Главный принцип — простота. Открыл, выбрал файлы, ткнул в устройство, готово.

## 2. Ключевые решения

| Решение | Выбор |
|---|---|
| Транспорт | Только локальная/маршрутизируемая сеть, прямое TCP-соединение |
| Обнаружение | Автопоиск в своей подсети + ручное добавление по IP |
| Сценарий отправки | Два шага: выбрать файлы → выбрать устройство |
| Приём | Диалог подтверждения; доверенные устройства принимаются молча |
| Что передаём | Файлы, папки целиком, share-меню Android. Текст/буфер — не в v1 |
| Целостность | Сверка CRC32 после каждого файла; битый переотправляется сам |
| Шифрование | Нет, открытый HTTP (см. п. 9) |
| Ориентация экрана | Портрет на всех платформах, включая десктоп |
| Языки | English (по умолчанию), Українська, Русский |

## 3. Пользовательские сценарии

### 3.1 Отправка

1. Пользователь добавляет содержимое двумя кнопками — **«Файл»** (выбор одного
   или нескольких файлов) и **«Папка»** (выбор каталога целиком). На десктопе
   работает и перетаскивание в окно, на Android — «Поделиться».
2. Выбранное показывается списком с именами, размерами и общим объёмом.
   Любой элемент можно убрать из списка.
3. Ниже — список устройств: найденные автоматически и добавленные вручную,
   с индикатором доступности.
4. Тап по устройству выбирает его — строка подсвечивается. Сам по себе тап
   ничего не отправляет, чтобы случайное касание не улетело не туда.
5. Внизу экрана закреплена кнопка **«Послать»**. Она неактивна, пока не
   выбраны и файлы, и устройство. Передача начинается по её нажатию. Отправка
   нескольким устройствам одновременно в v1 не поддерживается. Количество и
   объём на кнопке не повторяются — они уже в заголовке «Выбрано».
6. Слева от кнопки — галочка **«удалять оригиналы»**. С ней исходный файл
   удаляется у отправителя после того, как он принят и сверен на той стороне;
   кнопка при этом называется **«Перенести»**, так что режим виден в момент
   нажатия.

   Единица — файл, как и в п. 5.6: удаляется только то, что дошло, непрошедшее
   остаётся на месте, при отмене не удаляется ничего. Пустые папки после
   переноса остаются: пользователь просил перенести файлы, а снос каталогов —
   отдельное решение, которого никто не принимал. Каждое удаление пишется в
   лог передачи, и там же строкой сверху сказано, что передача была с
   удалением.

   Галочка не запоминается и не переживает передачу: это решение про конкретную
   пачку, а не настройка. После каждой передачи она снимается сама, иначе
   следующая отправка молча удалила бы ещё один набор файлов. По той же причине
   кнопка «Повторить» на неполной передаче никогда не удаляет.

### 3.2 Приём

1. Отправитель незнакомый → диалог: имя устройства, количество файлов,
   общий размер, кнопки «Принять» / «Отклонить» и галочка «Всегда доверять
   этому устройству». Без ответа 30 секунд → автоматически отклонить.
2. Отправитель в списке доверенных → приём начинается сразу, показывается
   только прогресс и уведомление по завершении.
3. Файлы пишутся в папку приёма. Структура папок из манифеста
   воссоздаётся. При конфликте имён к имени добавляется ` (1)`, ` (2)` и т.д.

### 3.3 Ход передачи

Прогресс-бар **один**, общий на всю передачу, и считается по байтам, а не по
количеству файлов: на паре фильмов с картинкой поштучный счёт врал бы, добавляя
за картинку сразу треть полосы. Под баром — строка с именем текущего файла и
счётчиком «3 из 12», рядом скорость и оценка оставшегося времени. Когда файл
один, общий прогресс и есть его прогресс, поэтому отдельная полоса на файл
нигде не нужна.
Координата шкалы — позиция в исходном порядке manifest: завершённый или
окончательно пропущенный файл занимает свой объявленный диапазон, а retry
повторяет тот же диапазон и не двигает шкалу назад. Поэтому progress монотонен,
ограничен общим размером и одинаков на обеих сторонах в terminal state.

Скорость и оставшееся время считаются по скользящему среднему за последние
5 секунд — мгновенное значение скачет и читать его невозможно.

Обе стороны видят одно и то же. Любая из сторон может отменить
передачу. На приёмнике файл пишется под временным именем и получает настоящее
только после сверки контрольной суммы, поэтому обрыв не оставляет
правдоподобно выглядящих огрызков: уже принятые файлы целые, недокачанный
исчезает. Если часть файлов не прошла, в строке передачи появляется кнопка
«Повторить» — она отправляет только их.

## 4. Интерфейс

Портретная компоновка, единая для всех платформ. На десктопе окно узкое и
вертикальное (минимальный размер 380×640, по умолчанию 420×800, изменяемое
по высоте). Material 3. Тема переключается в настройках: Системная, Светлая,
Тёмная. По умолчанию системная.

Всё приложение — **один экран**. Никакой нижней навигации и вкладок.

**Верхняя панель** — название приложения, имя этого устройства и единственная
кнопка-шестерёнка, открывающая настройки.

**Главный экран** сверху вниз:

1. Кнопки **«Файл»** и **«Папка»**. На десктопе область вокруг них принимает
   перетаскивание.
2. Список выбранного: имя, размер, крестик для удаления элемента. Общий объём
   и количество — строкой над списком.
3. Список устройств с индикатором доступности. Тап выбирает и подсвечивает.
4. Активные передачи — свои и входящие — показываются здесь же, сразу под
   списком устройств: один общий прогресс-бар, под ним имя текущего файла со
   счётчиком, скорость, оставшееся время и кнопка отмены. Ничего никуда
   переключать не нужно.
5. Завершённые передачи остаются в этом же списке до перезапуска приложения.
   Постоянной истории приложение не ведёт. Папку приёма открывает кнопка в
   заголовке раздела «Передачи», а тап по строке передачи — её лог.
6. Внизу закреплённая кнопка **«Послать»**, всегда видна при прокрутке, и
   слева от неё галочка «удалять оригиналы» (п. 3.1). Галочка на экране
   всегда, даже когда ничего не выбрано.

**Экран лога передачи** — тап по любой строке передачи, в обе стороны и на
любой стадии. Строка умеет сказать только итог, а лог отвечает, что случилось
с каждым файлом: принят или нет, коды ответов, причины отказов, по строке на
каждую неудачную попытку — так видно и сколько их ушло. Сверху — устройство,
счёт файлов, объём, время начала и ошибка передачи, если она была. Неудачи
выделены цветом ошибки. Кнопка в панели копирует весь лог текстом вместе с
версией сборки: цитировать его в баг-репорте с экрана телефона нечестно.

Лог живёт в памяти самой передачи: на диск не пишется, исчезает вместе со
строкой при перезапуске и ограничен 500 последними записями на передачу.

**Экран настроек** — имя этого устройства, папка приёма, язык интерфейса,
тема, порт, список доверенных устройств (с возможностью отозвать доверие),
приём в фоне (Android).
Имя непустое, занимает не более 256 байт UTF-8 и не содержит управляющих
символов; одна проверка применяется до сохранения и в обоих сетевых протоколах.

Добавленные вручную устройства живут не здесь, а в списке устройств на главном
экране, вместе с найденными автоматически: там их видно рядом с теми, кому
собираешься слать, там же крестик, чтобы убрать. Отдельный список в настройках
показывал бы те же строки во второй раз.

## 5. Сеть

### 5.1 Порт

UDP-обнаружение всегда слушает стабильный well-known порт **15353**. Поле
«Порт передачи» в настройках меняет только HTTP/TCP-сервер приёма. Этот номер
передаётся в JSON-анонсе, поэтому устройства с разными портами передачи всё
равно получают broadcast друг друга и подключаются к объявленному HTTP-порту.

Сборки со старой схемой совместимы автоматически, пока используют 15353.
Старой сборке с нестандартным общим UDP/TCP-портом устройство добавляется
вручную; после обновления обе стороны снова обнаруживаются автоматически.

Если порт занят другой программой, приложение не падает и не молчит: в
верхней части главного экрана появляется полоса с текстом об ошибке, номером
порта и кнопкой, ведущей прямо в настройки. Отправка при этом продолжает
работать — недоступен только приём. После смены номера сервер поднимается
без перезапуска приложения.

### 5.2 Обнаружение

Автопоиск работает **только внутри своей подсети** — широковещательные пакеты
маршрутизатор не пропускает по определению. Устройства за роутером добавляются
вручную по IP, см. п. 5.4. Разделение механизмов здесь принципиальное:
broadcast для «своих» без настройки, явный адрес для всех остальных.

UDP-broadcast на порт обнаружения, полезная нагрузка — JSON:

```json
{"t":"announce","id":"<uuid>","name":"Ноутбук","platform":"linux","port":15353}
{"t":"query","id":"<uuid>","name":"Телефон","platform":"android","port":15353}
```

- При старте, при смене сетевого интерфейса и далее каждые 5 секунд
  устройство рассылает `announce`. Пока discovery запущен, тот же цикл сверяет
  IPv4-интерфейсы, подключает новые, отключает исчезнувшие и при изменении сразу
  отправляет также `query`.
- Основной канал — link-local IPv4 multicast `239.255.53.53:15353`, группа
  подключается на каждом активном интерфейсе с TTL 1. Поэтому обнаружение не
  предполагает маску `/24` и работает в `/16`, `/20`, `/23` и других LAN.
  Limited broadcast `255.255.255.255` отправляется дополнительно для
  совместимости со старыми сборками. На Android multicast lock удерживается
  только пока discovery запущен, и живёт он в `Application`, а не в Activity:
  discovery работает и при свёрнутом приложении, то есть переживает любой
  отдельный экран.
- На полученный `query` устройство немедленно отвечает `announce` уникастом,
  чтобы новичок увидел всех сразу, не дожидаясь очередного цикла.
- `announce` отправляется только когда HTTP listener действительно привязан к
  настроенному порту, а корень приёма существует и доступен для записи. Ошибка
  приёма не отключает исходящие передачи и сохранённые вручную устройства.
- Автоматически найденное устройство, от которого не было анонсов 20 секунд,
  помечается офлайн и через минуту убирается из списка. К добавленным вручную
  это правило не относится, у них свой механизм — п. 5.4.
- Количество временных автоматически найденных записей и скорость добавления
  новых `id` ограничены; сохранённые вручную и доверенные записи в этот лимит не
  входят и никогда не вытесняются UDP-трафиком.
- Если точка доступа изолирует клиентов друг от друга (client isolation),
  автопоиск не сработает и в пределах одной подсети. Лечится только ручным
  добавлением, о чём говорится в подсказке при пустом списке устройств.
- `id` — постоянный идентификатор устройства, см. п. 5.3. Именно по нему
  работает доверие, а не по IP.

### 5.3 Идентификатор устройства

Доверие привязано к `id`, поэтому он обязан переживать переустановку
приложения — иначе после каждой переустановки все остальные устройства
перестанут узнавать это и снова начнут спрашивать подтверждение.

**Linux и Windows.** Обычный случайный UUID v4: генерируется при первом
запуске и лежит в `settings.json` (п. 10). Каталог настроек — `~/.config/EasySend`
и `%APPDATA%\EasySend` — переустановку приложения переживает, поэтому никаких
системных идентификаторов читать не нужно. У разных учётных записей на одной
машине свои каталоги, а значит и свои `id`, — это получается само собой.

**Android.** Здесь удаление приложения стирает приватное хранилище вместе с
настройками, поэтому `id` выводится из идентификатора устройства:

```
id = uuid_v5(EASYSEND_NAMESPACE, ANDROID_ID)
```

`Settings.Secure.ANDROID_ID` (пакет `android_id`) привязан к подписи APK:
переустановка сборки тем же ключом значение сохраняет, сбрасывается оно только
возвратом устройства к заводским настройкам. В сеть уходит не сам `ANDROID_ID`,
а необратимый хеш от него.

Если `ANDROID_ID` получить не удалось, генерируется случайный UUID, который
пишется и в настройки, и в файл `.easysend-id` внутри папки приёма; при старте
проверяются оба места, и второе позволяет восстановить прежний `id`.

### 5.4 Ручное добавление

Так добавляются устройства, до которых не доходит broadcast: за
маршрутизатором, в другой подсети, через VPN.

Пользователь вводит IP и, при необходимости, порт. Приложение выполняет
`GET /api/v1/info`, получает имя и `id`, добавляет устройство в постоянный
список. Такие устройства показываются всегда, даже когда офлайн, и не
исчезают при смене IP через DHCP — адрес можно отредактировать.

Анонсов от них не приходит, поэтому доступность определяется активно: тот же
`GET /api/v1/info` раз в 10 секунд с таймаутом 2 секунды. Опрос идёт только
пока приложение на переднем плане, чтобы не будить сеть впустую. Проверка
делается именно по HTTP, а не UDP-уникастом: она подтверждает работоспособность
ровно того канала, по которому пойдут файлы, включая проходимость фаерволов.

### 5.5 Протокол передачи

Обычный HTTP/1.1 на `HttpServer` из `dart:io`. Отдельный роутер вроде `shelf`
не нужен: шесть маршрутов — это несколько строк, а потоковым телом запроса
проще управлять напрямую.

**`GET /api/v1/info`**

```json
{"id":"<uuid>","name":"Ноутбук","platform":"linux","version":"1.0.0"}
```

**`POST /api/v1/prepare`** — запрос на передачу.

```json
{
  "senderId": "<uuid>",
  "senderName": "Телефон",
  "senderPort": 15353,
  "files": [
    {"id":"f1","path":"отчёт.pdf","size":2145728},
    {"id":"f2","path":"Фото/море.jpg","size":4812345}
  ]
}
```

Ответ `200`: `{"sessionId":"<uuid>"}` — принято целиком.
Ответ `403`: `{"reason":"declined"}` — отклонено пользователем или по таймауту.

`path` — относительный путь внутри передачи; так передаются папки: структура
едет в манифесте, а файлы идут обычным потоком, поодиночке.

`senderPort` — порт приёма отправителя. Адрес приёмник видит по соединению и
запоминает его вместе с портом: за маршрутизатором объявления не ходят, и
иначе доверенное устройство осталось бы без обратного адреса. Устройство,
которое до этого молчало, помечается как добавленное вручную — его опрашивают
по HTTP. Поле необязательное; без него берётся собственный порт приёмника.

**`POST /api/v1/upload?session=<id>&file=<fileId>`** — тело запроса это сырые
байты файла, потоком. Ответ `200` при полном совпадении принятого объёма с
заявленным в манифесте, иначе `400` и файл удаляется.

**`POST /api/v1/verify?session=<id>&file=<fileId>&crc=<hex>`** — сверка одного
файла сразу после его отправки. Ответ `200` — сошлось, файл получил настоящее
имя. Ответ `409` — не сошлось, недописанный файл удалён, `upload` можно
повторить.

**`POST /api/v1/finish?session=<id>`** — закрытие сессии: приёмник снимает
foreground service и показывает итоговое уведомление. Только успешный bounded
ответ позволяет отправителю показать `done`; отказ, timeout, разрыв или слишком
большое тело дают terminal error и best-effort `cancel`.

**`POST /api/v1/cancel?session=<id>`** — отмена всей сессии любой из сторон.

Файлы передаются последовательно, по одному запросу на файл. Чтение и запись
потоковые: файл любого размера не загружается в память целиком.

### 5.6 Целостность передачи

Проверка целостности не опция и не зависит от режима упаковки — она работает
всегда.

- Для каждого файла считается **CRC32, потоково и на лету**: отправителем по
  мере чтения, приёмником по мере записи. Второго прохода по диску нет — на
  файле в несколько гигабайт предварительный подсчёт означал бы чтение всего
  объёма дважды и заметную паузу перед стартом.
- Отправитель узнаёт свою сумму, только дописав файл до конца, поэтому сразу
  за телом файла уходит крошечный `verify` с этой суммой.
- Пока файл принимается, он лежит в служебном каталоге незавершённой сессии и
  получает настоящее имя только после успешной сверки.

**Единица атомарности — файл, а не сессия.** Каждый принятый и сверенный файл
сразу становится настоящим и больше никуда не денется. Это принципиально для
крупных передач: если из двух фильмов и картинки битой оказалась картинка,
переотправляется одна картинка, а не всё заново.

Обратная сторона — при обрыве в папке приёма остаются уже принятые файлы, а
недокачанный исчезает вместе с `.part`. Половинок с настоящими именами не
бывает никогда, так что «принятый файл» всегда означает «целый файл».

### 5.6.1 Что происходит при несовпадении

1. Приёмник отвечает `409`, удаляет временный файл и ждёт повтора.
2. Отправитель **молча переотправляет** этот файл, до двух попыток. Спрашивать
   тут нечего: сбой почти всегда случайный, а пользователя может не быть у
   экрана — вопрос просто остановил бы передачу на неопределённый срок.
3. Остальные файлы очереди при этом не задерживаются.
4. Если и повторы не прошли, файл помечается неудачным, а передача идёт
   дальше. По её окончании в списке передач остаётся строка вида «принято 2 из
   3, не удалось: `poster.jpg`» с кнопкой **«Повторить»**, которая заново
   отправляет только непрошедшие файлы.

То есть вопрос пользователю задаётся один раз и постфактум, когда уже понятно,
что автоматика не справилась, — и стоит этот вопрос ровно одну кнопку.

CRC32 выбран намеренно вместо криптографического хеша: он ловит случайные
искажения, стоит копейки по процессору и не притворяется защитой от подмены —
её без шифрования канала всё равно нет (п. 9).

Небольшие управляющие тела (`prepare` в обе стороны) ограничены и размером, и
общим wall-clock deadline, и паузой между байтами. Поэтому peer не может держать
единственный слот бесконечно, присылая по байту чуть чаще inactivity timeout.
Для содержимого файлов общего deadline нет: там остаётся только обновляемый
реальным прогрессом inactivity timeout.

Приёмник подтверждает запись каждого сетевого chunk файловому consumer до
чтения следующего. Это связывает скорость сети со скоростью накопителя и не
позволяет очереди ожидающих записи данных расти вместе с размером файла.

### 5.7 Обязательные проверки на приёмнике

- `path` из манифеста нормализуется и проверяется: отклоняются абсолютные
  пути, `..` в любом сегменте, двоеточие, а также зарезервированные имена
  Windows (`CON`, `PRN`, `NUL`, `COM1`…). Итоговый путь обязан лежать внутри
  папки приёма — это проверяется после канонизации, а не только по строке.
- Разделитель на проводе всегда `/`. Обратный слеш отклоняется **на всех
  платформах**, а не трактуется как второй разделитель: на Windows он
  разделяет папки, в Linux и Android это обычный символ внутри имени, и одно
  и то же имя не может значить разное на двух концах передачи. Отправитель
  предлагает заменить его на дефис при выборе файлов — с показом имени и
  причины; без согласия пользователя файл не уезжает.
- Длина имени считается в символах UTF-16, как её считают NTFS и ext4:
  255 на компонент. Байты здесь были бы чужой меркой — кириллическое имя
  из 150 букв весит 300 байт и файловым системам не мешает.
- Сессия без предшествующего `prepare` отклоняется.
- Приём сверх заявленного в манифесте размера обрывается.
- Одновременно обслуживается одна сессия приёма; параллельный `prepare`
  получает `409`.

## 6. Папка приёма по умолчанию

Подкаталог `EasySend` внутри системной папки загрузок:

| Платформа | Путь |
|---|---|
| Android | `/storage/emulated/0/Download/EasySend` |
| Linux | системная папка загрузок + `/EasySend` |
| Windows | системная папка загрузок + `\EasySend` |

На Linux путь берётся из `XDG_DOWNLOAD_DIR` (`xdg-user-dir DOWNLOAD`), а не
хардкодится как `~/Downloads` — у локализованных систем каталог называется
иначе, например «Загрузки». На Windows — через известную папку `Downloads`,
не через склейку с `%USERPROFILE%`. Если системный путь определить не удалось,
запасной вариант — каталог документов приложения.

Каталог создаётся при первом приёме. Меняется в настройках.

## 7. Платформенные особенности

**Android.** Разрешения на доступ к файлам и уведомления. Пункт в системном
меню «Поделиться» — приложение открывается с уже подставленными файлами,
остаётся выбрать устройство и нажать «Послать».

*Работа при погашенном экране и свёрнутом приложении.* Свёрнутое приложение
живёт недолго: процесс могут выгрузить под нехватку памяти, а после гашения
экрана устройство уходит в Doze, где фоновым приложениям обрезается сеть и
засыпает Wi-Fi. Поэтому на время активной передачи, в любую сторону:

- один Flutter engine принадлежит `Application`, а Activity только временно к
  нему прикрепляется. Уничтожение и повторное создание Activity не уничтожает
  Dart isolate, сервер или discovery и не регистрирует плагины и channel заново;

- **экран не гасится** — пока идёт передача и приложение на экране, включается
  wakelock экрана, чтобы таймаут блокировки не срабатывал прямо посреди
  процесса. Снимается сразу по завершении;
- поднимается foreground service типа `dataSync` с уведомлением и прогрессом —
  он нужен на случай, если приложение всё же свернут: без него процесс могут
  выгрузить;
- берутся частичный wakelock процессора и `WifiLock` в режиме высокой
  производительности, чтобы засыпание Wi-Fi не рвало соединение.

Всё перечисленное снимается по окончании передачи, вхолостую ничего не
удерживается.

*Приём, когда передачи нет,* управляется переключателем «Принимать в фоне» в
настройках, по умолчанию выключенным:

- выключен — сервер и анонсы работают, только пока приложение на экране;
  свернули, и устройство просто пропадает из списка у отправителя. Предсказуемо
  и ничего не расходует;
- включён — постоянный foreground service типа `specialUse` (на Android 14+)
  с уведомлением «Готов принимать»,
  приём работает и при погашенном экране. Рядом с переключателем предложение
  исключить приложение из оптимизации батареи: без этого Doze всё равно будет
  рвать соединения на длительном простое. Активная передача переключает сервис
  в `dataSync`; если Android 15+ исчерпает его системный лимит, сервис немедленно
  снимает locks и уведомление и останавливается без падения процесса. Намерение
  пользователя «Принимать в фоне» сохраняется, а интерфейс сообщает, что
  фоновая готовность временно недоступна. Если приложение в этот момент
  свёрнуто, текущая передача отменяется и сетевые listeners закрываются: сокеты
  не продолжают скрытно работать без foreground service. Возврат приложения на
  экран восстанавливает поддерживаемый режим.

*Закрытие приложения* согласовано с этим переключателем. Когда «Принимать в
фоне» выключен, ✕ закрывает приложение целиком: сокеты, анонсы и сервис
останавливаются, карточка приложения убирается из списка недавних. Когда
переключатель включён и фоновая готовность не потеряна, ✕ закрывает только
экран — приём, сервис и уведомление продолжают работать, иначе включённый
переключатель ничего бы не значил. Вопрос при этом не задаётся: активная
передача продолжается в фоне, терять нечего. Вернуться на экран можно нажатием
на уведомление.

Само уведомление несёт кнопки. «Стоп» появляется только во время передачи и
обрывает её, оставляя приём включённым. «Выход» есть всегда и завершает
приложение полностью — это единственный выход, который не сохраняет приём. Если
выходу есть о чём спросить (идёт передача или включено подтверждение выхода),
кнопка сначала открывает приложение и задаёт вопрос на экране: с Android 12
уведомление не может поднять экран через сервис.

Разрешение на уведомления — обязательная capability этого режима. Отказ не
включает переключатель, а отзыв уже выданного разрешения отключает фоновый
режим при следующей сверке. Если consent-уведомление всё же нельзя показать,
неизвестный отправитель получает обычный отказ; доверенным отправителям и
диалогу на открытом экране это не мешает.

*Подтверждение при свёрнутом приложении.* Диалог показать некому, поэтому
запрос приходит уведомлением с кнопками «Принять» и «Отклонить», тап по самому
уведомлению открывает приложение. Те же 30 секунд на ответ.

*Если процесс всё-таки убит* посреди приёма, подчистить мусор в тот момент
некому — поэтому файлы пишутся в помеченный служебный каталог сессии и получают
настоящее имя только после полной сверенной записи. Оставшиеся служебные
каталоги EasySend удаляются при следующем запуске; пользовательские файлы и
похожие по имени каталоги не затрагиваются.

**Linux и Windows.** Перетаскивание файлов и папок в окно. Клик по завершённой
передаче открывает файл или его папку системными средствами. Окно запоминает
размер и позицию.

## 8. Локализация

Три локали: `en` (по умолчанию и запасная), `ua`, `ru`. Язык определяется по
системному, переопределяется в настройках. Ключ украинской локали — `ua`, а
не ISO-код `uk`: системный `uk` приводится к нему при первом запуске, и это
единственное место, где перевод кода вообще нужен.

Никаких строк в коде — всё через `lw('key')`. Файлы локализации содержат
только чистые строки без знаков препинания; точки, двоеточия и многоточия
добавляются в коде. Каждая новая строка добавляется сразу во все три локали
полностью переведённой.

## 9. Безопасность — сознательные ограничения

Трафик не шифруется. Это осознанный выбор в пользу простоты для доверенной
домашней или офисной сети, и у него есть цена:

- Любой в той же сети может прочитать передаваемые файлы.
- Отправителя можно подделать: доверие привязано к `id`, который никак не
  подтверждается криптографически.

Приложение не должно использоваться в публичных и гостевых сетях. Формулировка
об этом выводится один раз при первом запуске и доступна в настройках.

Сверка CRC32 (п. 5.6) защищает только от случайных искажений, но не от
подмены: тот, кто способен подменить данные в пути, пересчитает и сумму.

Архитектурно закладывается возможность включить TLS позже: весь сетевой код
работает через единую фабрику клиента и сервера, так что переход на HTTPS
локализуется в одном месте.

## 10. Архитектура и стек

Раскладка плоская, без вложенных каталогов — как в соседнем проекте bikelog,
чтобы не заводить вторую традицию на одного разработчика:

```
lib/
  main.dart              точка входа, окно, тема, локаль
  globals.dart           константы, темы, lw(), xdef; ре-экспортит хелперы
  models.dart            Device, FileItem, TransferSession
  settings_helpers.dart  пути, settings.json, идентификация устройства
  file_helpers.dart      сбор файлов и папок, санация путей, уникальные имена
  ui_helpers.dart        диалоги и цветные снекбары
  net_discovery.dart     UDP-анонсы и список устройств
  net_server.dart        HTTP-сервер приёма
  net_sender.dart        клиент отправки
  home_screen.dart       единственный основной экран
  settings_screen.dart
assets/
  locales.json           переводы, ключ записи — английская строка
```

Всё общее — константы, модели, форматирование размеров и скорости, `lw()` —
доступно через один импорт `globals.dart`, который ре-экспортит остальные
хелперы. Дублирования между модулями нет.

Отдельной библиотеки управления состоянием нет: хватает `setState` и
`ValueNotifier` на общий пересбор приложения при смене языка или темы. Тянуть
Riverpod ради этого незачем.

Все настройки, доверенные устройства и добавленные вручную адреса лежат в
одном файле `settings.json` — формат читаемый и правится руками:

| Платформа | Каталог |
|---|---|
| Linux | `$XDG_CONFIG_HOME/EasySend`, при отсутствии переменной `~/.config/EasySend` |
| Windows | `%APPDATA%\EasySend` |
| Android | приватный каталог приложения |

Пути на десктопе собираются явно, а не через `getApplicationSupportDirectory()`:
на Linux эта функция вернула бы `~/.local/share/…`, а на Windows — вложенность
вида `%APPDATA%\<company>\<product>`. Нужен ровно `EasySend` одним уровнем.

Каталог создаётся при первом сохранении. Если файл повреждён или не читается,
приложение стартует с настройками по умолчанию, а испорченный файл
переименовывается в `settings.json.bad` вместо молчаливой перезаписи.

Зависимости: `file_picker`, `path`, `path_provider`, `device_info_plus`,
`uuid`, `android_id`, `window_manager`, `desktop_drop`,
`receive_sharing_intent`, `flutter_local_notifications`, `permission_handler`,
`wakelock_plus`, `archive` (только ради инкрементального CRC32).

Foreground service написан своим кодом на Kotlin (`TransferService.kt`) поверх
`MethodChannel`, без `flutter_foreground_task`: тому нужен отдельный изолят,
тогда как сервис требуется ровно в том же процессе, где живут сокеты.

Локальный IP берётся из `NetworkInterface.list()` в `dart:io`, отдельный пакет
для этого не нужен. Папка загрузок — из `getDownloadsDirectory()`, который уже
умеет и `XDG_DOWNLOAD_DIR`, и известную папку Windows; вручную собирается
только каталог настроек.

Android release собирается транзакционно: новая версия сохраняется только
после появления всех обязательных непустых APK под окончательными именами и их
проверки. Ошибка build/collection/rename/listing до этой точки восстанавливает
оба файла версии и исходные build outputs, не перезаписывая старые artifacts.

## 11. Модели данных

```dart
class Device {
  String id;            // постоянный UUID устройства
  String name;
  String platform;      // android | linux | windows
  String address;       // IP
  int port;
  bool trusted;         // принимать от него молча
  bool manual;          // добавлено вручную, не исчезает офлайн
  DateTime? lastSeen;
}

class FileItem {
  String id;
  String relativePath;  // путь внутри передачи
  String? sourcePath;   // локальный путь, только у отправителя
  int size;
  int? crc32;           // считается на лету, известен по завершении файла
}

class TransferSession {
  String id;
  bool incoming;
  String peerName;
  List<FileItem> files;
  int bytesTotal;
  int bytesDone;
  TransferStatus status; // pending, active, done, cancelled, failed
  DateTime startedAt;
  String? error;
  List<TransferEvent> events; // лог передачи, только в памяти
}

class TransferEvent {
  DateTime at;
  String? file;    // относительный путь; пусто — событие обо всей передаче
  String message;  // ключ локализации, переводится при показе
  String? detail;  // коды и системный текст, не переводится
  bool failure;    // строка показывается цветом ошибки
}
```

## 12. Что не входит в v1

- Передача через интернет и релей-серверы.
- Отправка текста, ссылок и буфера обмена.
- Шифрование канала.
- Докачка прерванной передачи.
- Отправка нескольким устройствам сразу.
- Постоянная история передач между запусками.
- iOS и macOS.

## 13. Критерии готовности

1. Два устройства в одной подсети видят друг друга без настройки за 5 секунд.
2. Устройство в другой подсети добавляется по IP, показывает актуальный
   статус доступности и принимает файлы.
3. Занятый порт даёт понятное сообщение со ссылкой в настройки, а не тихий
   отказ приёма.
4. Папка на 500 файлов передаётся с сохранением структуры.
5. Файл на 4 ГБ передаётся без роста потребления памяти.
6. Отмена или обрыв не оставляют в папке приёма файлов с настоящими именами,
   кроме тех, что уже полностью приняты и сверены.
7. Искажённый файл ловится сверкой CRC32, переотправляется автоматически и не
   заставляет повторять всю передачу; уцелевшие крупные файлы остаются на
   месте.
8. Разрыв Wi-Fi во время передачи даёт понятную ошибку, а не зависание.
9. На Android передача не прерывается, если свернуть приложение; экран во
   время неё не гаснет сам, а убитый процесс не оставляет в папке приёма
   файлов с настоящими именами.
10. После переустановки приложения устройство остаётся доверенным на другой
    стороне — `id` не изменился, диалог подтверждения не появляется.
11. Манифест с `../` не может записать файл вне папки приёма.
12. Интерфейс полностью переведён на все три языка, без английских заглушек.
